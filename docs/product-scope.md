# Feed Passport product scope

## Product promise

Feed Passport gives a person a portable, inspectable policy for the recommendation environment they want. In deterministic Feed Passport Lab and ten account-free platform control twins it translates that policy, applies only approved local controls, measures the result, adapts within fixed action and iteration budgets, and leaves auditable rollback receipts. For real external destinations, this checkout compiles declared capabilities into guided plans without executing or measuring a social account.

The product transfers intent and observable preferences. It never claims to copy proprietary model weights, hidden embeddings, watch history, or an exact platform algorithm.

The current implementation has three distinct evidence levels. `feed_passport_lab` is the reference closed-loop adapter. Each `twin:<platform>` adapter reuses deterministic local state while limiting execution to that platform profile's declared control semantics; twins make no network calls and do not reproduce a private ranker. Each unprefixed external-platform adapter remains a credential-free planner: the runtime injects one explicitly labeled dummy-account snapshot per platform for capture and compilation tests, then produces guided plans and translation loss. Arbitrary account IDs with no authorized observation fail closed. Browser cards labeled **Selected** or **Included** are local itinerary state rather than real account connections; the WebMCP field name `connectedDestinations` represents the same selection state.

Model assistance is a separate, narrower evidence boundary rather than a fourth adapter level. A top-level feature clerk may propose one typed migration, temporary-visa, or companion configuration from a server-derived safe catalogue. A separate mission planner may propose a subset of controls for one already selected twin. Both use a pinned local Qwen model through llama.cpp, never change an adapter's evidence level, and have no route to a real account.

## Primary audience and hero workflow

The primary user is changing accounts or platforms and does not want to spend weeks manually retraining recommendations.

The hero request is:

> Bring independent games, design, and local culture from my old account. Keep outrage below five percent, preserve twenty percent serendipity, and never like, post, comment, repost, or message anyone.

In the Agent mission desk, the user chooses a local control twin, writes an outcome, and fixes acceptance thresholds plus total, per-pass, and iteration budgets. The user can ask the local model to plan or use the deterministic preview directly. A model-assisted request creates a fresh Strands planner that must inspect the server-selected Passport, inspect the server-selected control surface, and submit one proposal, in that exact order. It may narrow the available action families and explain why; it cannot change the actor, Passport, twin, account scenario, budgets, thresholds, minimum improvement, consent, execution, or rollback.

Deterministic preview then persists the mission and shows before and counterfactual measurements, the admitted initial controls, action-family allowlist, policy stages, planner evidence when present, and consent checkpoint without mutating state. A one-time mission-bound approval allows the runner to observe, evaluate, plan, act, re-observe, and adapt or stop. Adaptation may recompile targets only within the same Passport version, approved action families, and remaining budgets; it is not restricted to the exact initial target IDs. Receipts and the mission stop reason remain inspectable, and rollback requires a separate approval and processes receipts in reverse order. For a real external platform, the product still stops at an honest guided plan or translation loss.

## Complete feature set

- Passport capture, plain-language editing, structured editing, import, export, versioning, templates, and checkpoints.
- Closed-loop account migration in Lab, plus bounded local agent missions across ten `twin:<platform>` control-surface simulators, plus external-platform translation previews and guided handoffs with explicit loss. No live external execution or verification is claimed.
- Temporary Visas as expiring Passport overlays. Both current demo modes target Lab; `Reversible Lab` executes approved local controls and rolls them back on expiry or revocation.
- Travel Companions as continuously refreshed effective projections supporting common-ground, taste-swap, bridge, and weighted modes. Two distinct local test principals must independently create selected-field, self-targeted, expiring consent slices; either revocation or expiry disables the projection while both base Passports remain immutable.
- Drift Watch with scheduled Lab observation, confidence thresholds, bounded automatic correction, alerts, and an emergency stop. An app-owned FastAPI lifespan runner advances persisted due jobs every five seconds by default.
- Serendipity budgets, diversity targets, source caps, hard exclusions, languages, formats, and sensitive-topic privacy controls.
- A counterfactual preview, deterministic Proof Lab, seeded twin accounts, equal action budgets, and machine-readable evaluation receipts.
- Creator Continuity using deterministic browser-to-directory fixture mappings. Unknown matches are explicitly flagged for human confirmation; this checkout does not yet provide a workflow for adding a new reviewed directory link. Studio A and Paper Lab map through Lab lookup aliases even though their cards display Bluesky as the source; real-platform identity verification is not claimed.
- A template library for temporary contexts without sharing raw history.
- Capability manifests and guided planning adapters for major networks, paired with deterministic local control twins. Lab and the twins close loops only over local simulated state; no external adapter is live-certified in this checkout.
- Two request-bound local Strands protocols. The feature clerk calls `inspect_selected_passport`, `inspect_safe_feature_catalog`, and one kind-specific typed submission tool; the mission planner calls `inspect_selected_passport`, `inspect_selected_control_surface`, and `submit_mission_proposal`. Both are proposal-only, exact-order, loopback-only paths with genuine local-model proof. Feature-clerk tool payloads contain no prose: deterministic templates render the display text and bind migration language to the exact capability record.
- Six WebMCP tools on the Feed Passport site: inspect product state, preview migration, prepare a temporary visa, open rollback, preview a local mission, and inspect a local mission. No WebMCP tool approves or executes a mission.

## Non-negotiable trust boundaries

- The current localhost API treats validated `actor_id` values as deterministic test principals, not authenticated identities. Any network-exposed deployment must bind owners through authenticated middleware before these owner checks can be treated as authorization.
- Explicit approval is required before account mutation.
- The user approves an action envelope with action types, counts, destinations, expiry, and stop conditions.
- This checkout stores no external-platform OAuth credentials and has no live transport. Any future authorized deployment must encrypt credentials at rest, redact them from logs, and keep them outside model context.
- Raw private history is not transferred between partners or platforms. Only an explicit Passport slice may be shared.
- Public engagement automation is denied.
- The local model receives no owner identity, account credentials, raw history, partner identity, consent object, approval token, execution tool, or rollback tool. Request prose is untrusted input. The feature clerk may return only typed categorical and numeric fields; deterministic code renders its user-facing explanation. The mission planner's bounded prose is still intersected with deterministic policy before any approval exists.
- Local inference accepts only an explicitly configured plain-HTTP loopback llama.cpp endpoint. It has no paid, external, or default-provider fallback.
- Model-facing agent paths may schedule alert-only monitoring, but cannot create a future mutation mandate; bounded automatic monitoring stays behind the explicit local UI/API surface.
- Unsupported controls return structured translation loss instead of fabricated success.
- Every mutation is idempotent and records before-state, outcome, reversibility, and provenance.
- Rollback restores reversible actions and explicitly names platform learning that cannot be undone.
- Local destination selection is never presented as authentication or account connectivity.
- A `twin:<platform>` label always means deterministic control-surface simulation. It is never evidence of the named platform's feed, ranking fidelity, account access, or API conformance.

## Originality boundary

Threads now offers native temporary algorithm requests and limited preference copying. Feed Passport therefore does not position either feature alone as novel. Its differentiator is portable cross-platform intent, capability-aware compilation, consent, measurable verification, policy enforcement, and rollback across heterogeneous networks.

## Acceptance definition

The local product is complete when the Lab workflows and persisted control-twin mission are executable through the public API and user interface, feature and mission previews are non-mutating, consent and budgets fail closed, mission and continuous-companion state survive a service restart, either companion source revision refreshes only consented fields, revocation/expiry removes the effective blend, the app-owned lifespan runner processes persisted activation, expiry, and monitor jobs without a manual endpoint, rollback remains deterministic and verifies the local control-state fingerprint, and the evaluation suite records before/after evidence. Model-assisted paths must additionally prove exact three-tool proposal sequences, server-locked authority, and zero paid or external model calls; any executing mission must still reach `awaiting_approval` before mutation.

Local completion has no AWS requirement. The included AgentCore entrypoint is a deterministic-command-only packaging seam; it rejects broad free-text chat and does not supply a model fallback. Any AWS or managed AgentCore integration is optional future deployment work that requires separate user authorization and is not part of the local proof.

All unprefixed external adapters currently remain Guided. A local twin does not promote its paired external adapter. A future external adapter may be promoted only to the level demonstrated by an authorized live-account conformance run; developer documentation, a selected UI card, a dummy snapshot, or a passing twin run is not certification.
